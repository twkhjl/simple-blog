# UI Refresh Spec v1

## 1. 文件目的

本文定義現有部落格專案之前端 UI 改版方向。目標是導入 `page_example` 內靜態頁面的視覺語言，完成整體介面升級，同時維持既有功能、既有主要路由與既有資料流程不變。

本文件只描述設計與實作邊界，不包含實際程式修改步驟。任何公開文件內容均需維持去識別化，不記錄真實帳號、郵件、網域、金鑰或部署端點。

## 2. 背景

目前前端功能已具備基本可用性，但頁面樣式仍接近原生 HTML 結構：

- 前台頁面缺少品牌感與閱讀節奏。
- 登入 / 註冊 / 個人資料頁面缺少一致的表單視覺語言。
- 後台頁面資訊層級弱，缺少控制台感與操作焦點。
- 全站尚未建立可重用的設計 token 與元件樣式基礎。

`page_example/stitch_neumorphic_dark_cms_template` 已提供一套完整的深色 neomorphic 視覺參考，包含前台文章列表、文章詳情、登入頁、後台 dashboard、文章編輯頁與元件庫，適合作為本次 UI 改版的主要靈感來源。

## 3. 目標

### 3.1 主要目標

- 將全站 UI 升級為高度貼近 `page_example` 的深色 neomorphic 風格。
- 保留現有功能行為、API 互動方式與主要資料結構。
- 建立可重用的全域設計 token 與共用樣式基礎。
- 讓前台、登入流程與後台介面維持同一套設計語言，但根據使用情境調整資訊密度。

### 3.2 次要目標

- 提升頁面層級辨識、閱讀體驗與互動反饋。
- 改善空狀態、載入狀態與訊息提示的視覺一致性。
- 為後續新增頁面保留可延伸的樣式架構。

## 4. 非目標

- 不在本階段更動後端 API 規格。
- 不在本階段新增需要後端支援的新功能。
- 不以像素級複製 `page_example` 為目標。
- 不為了套用範例而引入假資料或虛構指標。
- 不進行與 UI 改版無關的大型重構。

## 5. 設計來源與採用策略

### 5.1 主要來源

- `aurablog_landing_page`
- `blog_list`
- `blog_detail`
- `login_page`
- `admin_dashboard`
- `post_editor`
- `ui_components_library`
- `obsidian_depth/DESIGN.md`

### 5.2 採用方式

本次不直接搬用靜態 HTML，而是抽取以下設計語言後套入既有 Vue 頁面：

- 深色霧面背景
- 大圓角容器
- 外凸 / 內凹陰影層次
- 紫色主光、青色輔助光
- 高對比字色與偏技術感標籤
- 輕量發光效果與精簡動態

### 5.3 不直接照抄原因

- 現有資料欄位較少，硬搬版型會造成資訊空洞。
- 後台操作頁需要比展示頁更重視辨識與效率。
- 深色 neomorphic 若過度使用，會降低表單、按鈕與表格的可讀性。

## 6. 整體設計原則

### 6.1 風格定位

整體視覺定位為「深色控制台式部落格介面」：

- 前台像沉浸式數位刊物
- 後台像精緻內容控制台
- 表單像嵌入式儀表面板

### 6.2 視覺原則

- 高度貼近範例氣質，但不犧牲可讀性。
- 同一設計語言套用到全站，不做前後台割裂風格。
- 靠深度、光影與容器階層表達資訊層級，不靠過多邊框。
- 控制發光效果使用量，避免畫面失焦。

### 6.3 可用性原則

- 所有操作元素需保有明確 hover / focus / active 狀態。
- 表單輸入區需維持足夠對比，不可因內凹效果造成辨識困難。
- 文章閱讀區需優先保證排版與行距，不讓裝飾效果壓過內容。
- 後台資訊列表需優先保證掃描效率。

## 7. 範圍

### 7.1 本次涵蓋頁面

- `/`
- `/post/:slug`
- `/login`
- `/register`
- `/profile`
- `/admin`
- `/admin/posts`
- `/admin/posts/new`
- `/admin/posts/:id/edit`

### 7.2 可接受的補充頁面

若為了視覺完整性需要新增純前端輔助頁面或局部空狀態視圖，可新增；但不得引入新的核心業務流程，也不得要求後端新增 API 才能成立。

預設情況下，應優先在既有頁面內完成改版，不以新增頁面作為主要手段。

## 8. 現有資料約束

本次 UI 改版必須以現有前端已使用的資料結構為基礎，不得因視覺需要而假設新的後端欄位。

### 8.1 前台文章列表可用欄位

首頁文章清單可依既有資料使用以下資訊：

- `title`
- `slug`
- `excerpt`
- `coverImageUrl`
- `publishedAt`

不可假設存在分類、標籤、閱讀時間、文章統計數、置頂狀態等欄位。

### 8.2 前台文章詳情可用欄位

文章詳情頁可依既有資料使用以下資訊：

- `title`
- `excerpt`
- `content`
- `coverImageUrl`
- `author.displayName`
- `publishedAt`

若 `author.displayName` 或 `publishedAt` 為空，畫面需優雅退化，不可顯示假名稱、假日期或 placeholder 假資料。

### 8.3 個人資料頁可用欄位

個人資料頁可依既有資料使用以下資訊：

- `email`
- `role`
- `displayName`
- `status`

若 `status` 目前尚未在畫面使用，可保留於設計層規劃，但不得為了呈現狀態而改動既有 API 流程。

### 8.4 後台文章列表可用欄位

後台文章列表可依既有資料使用以下資訊：

- `title`
- `slug`
- `status`
- `authorDisplayName`
- `publishedAt`
- `updatedAt`

因此列表可以做出較完整的管理視圖，但仍不可假設存在瀏覽量、留言數、SEO 分數或工作流節點資料。

### 8.5 後台文章編輯頁可用欄位

後台編輯頁可依既有資料使用以下資訊：

- `title`
- `slug`
- `excerpt`
- `content`
- `coverImageKey`
- `status`
- `authorDisplayName`
- `publishedAt`
- `createdAt`
- `updatedAt`

如需顯示 metadata 區塊，應優先使用以上欄位，不得新增需後端配合的編輯控制。

## 9. 頁面層級設計策略

### 9.1 Public Layout

Public Layout 應改為品牌化外殼，而非單純導覽列加內容區：

- 頂部導覽改為深色浮雕式導航艙
- 主視覺區可加入大標題、簡短說明與背景光暈
- 內容區採卡片式節奏排列
- Footer 可補足簡潔品牌尾段，但不新增功能

### 9.2 Home Page

首頁應對照 `blog_list` 的語言進行重構：

- 建立 hero 區塊，承接站點定位與最新文章入口
- 文章清單改為卡片式列表，而非純文字條列
- 每篇文章呈現標題、摘要、日期資訊與閱讀入口
- 載入中、錯誤、空資料狀態需有一致卡片包裝
- 若 `coverImageUrl` 存在，可用於卡片或 hero 視覺；若不存在，需有一致 fallback 造型

### 9.3 Post Detail Page

文章詳情頁應對照 `blog_detail`：

- 使用聚焦閱讀容器
- 標題、摘要、內文分層明確
- 內容區保留長文可讀性，避免過重裝飾
- 若 `publishedAt` 或作者資訊存在，應以輕量 metadata 呈現
- 可加入返回列表的輔助導引，但不改變主功能

### 9.4 Login / Register

登入與註冊頁應對照 `login_page`：

- 採集中式表單卡
- 表單欄位使用內凹風格
- 主 CTA 使用外凸發光按鈕
- 錯誤 / 成功訊息改為一致狀態區塊

### 9.5 Profile Page

Profile Page 應延續 auth 頁的表單語言，但加入帳號資訊展示區：

- 帳號資訊與可編輯欄位分區
- 角色、email、狀態可採只讀資訊卡樣式
- `displayName` 編輯區保留明確可操作焦點

### 9.6 Admin Layout

Admin Layout 應對照 `admin_dashboard` 與 `ui_components_library`：

- 導覽區改為控制台感側重或頂部艙體
- 後台內容區採較高資訊密度的卡片網格
- 風格與前台一致，但降低裝飾比例、提高掃描性

### 9.7 Admin Dashboard

Dashboard 雖目前資料有限，仍應建立可用的控制台首頁：

- 顯示歡迎區塊
- 顯示內容管理導引卡
- 若可從既有文章列表推導簡單數量，可呈現文章數量 / 狀態摘要
- 若無法穩定取得額外資訊，優先維持靜態引導卡，不補假數據

### 9.8 Admin Post List

文章列表頁應改為管理導向列表：

- 保留建立新文章入口
- 將文章清單改為卡片列或帶狀列表，不使用原始 `ul`
- `status` 以 badge 呈現
- 每列需清楚表達標題、狀態、作者 / 日期類資訊與編輯入口

### 9.9 Admin Post Edit

文章編輯頁應對照 `post_editor`：

- 表單分為主要內容區與操作側欄，或單欄分段卡片
- `title`、`slug`、`excerpt`、`content`、`status` 各自明確分組
- 若 `authorDisplayName`、`createdAt`、`updatedAt`、`publishedAt` 可取得，應整理於次要 metadata 區
- 刪除操作需與儲存操作做危險層級區隔
- 表單訊息、載入狀態、提交中狀態需清楚可辨識

## 11. 元件與樣式系統

### 11.1 全域設計 Token

至少應建立以下 token 類別：

- 背景色階
- 表面色階
- 文字色階
- 主色 / 輔色 / 危險色
- 外凸陰影
- 內凹陰影
- 大圓角 / 中圓角 / pill 圓角
- 間距節奏
- 字級階層
- 動畫時間

### 11.2 基礎元件樣式

至少需統一以下元素外觀：

- 按鈕
- 連結樣式
- 文字輸入框
- 文字區域
- 下拉選單
- 表單欄位標籤
- 卡片容器
- badge
- 訊息提示區
- loading / empty / error state 容器

### 11.3 互動狀態

所有可互動元件需定義：

- default
- hover
- focus-visible
- active
- disabled

危險操作需額外有警示色與不同陰影語言。

### 11.4 缺圖與缺資料 fallback

本次需明確定義 fallback 呈現原則：

- 無封面圖時，以漸層、幾何光影或品牌字首占位，不顯示破圖
- 無作者名稱時，隱藏作者欄位或顯示中性文案，不製造假名稱
- 無日期時，隱藏日期欄位，不顯示假時間
- 無資料列表時，使用完整 empty state 卡片，不顯示空白頁

## 12. 排版與響應式策略

### 12.1 Desktop

- 保留較寬留白，凸顯 neomorphic 深度
- 首頁與後台頁可使用雙欄或網格編排
- 編輯頁可視情況使用主編輯區 + 次要控制區

### 12.2 Mobile

- 優先單欄堆疊
- 保留視覺語言，但降低大面積陰影的擁擠感
- 導覽、表單、卡片需維持可點擊尺寸

### 12.3 文章閱讀

- 控制每行字數
- 提升段落間距
- 長文區與背景層次需清楚分離

## 13. 可用性與可近用性基線

本次雖以視覺升級為主，仍應維持基本可近用性：

- 鍵盤可聚焦元素需有明確 focus-visible 樣式
- 表單 label 與欄位對應關係需保留
- 主要文字與背景需維持可讀對比
- 狀態不得只靠顏色區分，必要時需搭配文字
- 危險操作需有更高辨識度，不得與一般儲存按鈕混淆

## 14. 動效原則

動效以輕量為主：

- 頁面載入可用淡入與位移
- 卡片 hover 僅做微幅升起或光影變化
- 按鈕按下時應由外凸轉向較內凹的觸感反饋

不得使用過多持續性動畫，避免干擾閱讀與管理操作。

## 15. 技術策略

### 15.1 實作方式

- 以現有 Vue 3 + Vite 架構內完成
- 以全域 CSS 與頁面 class 重整為主
- 必要時抽出共用展示元件，但避免為了樣式過度元件化
- 不以導入大型 UI framework 作為前提

### 15.2 樣式建議

- 在 `frontend/src` 建立全域 theme 基礎
- 以 CSS custom properties 管理色彩、陰影、圓角、間距
- 將 layout 與 page-specific 樣式分層整理
- 將基礎 reset / theme / layout / page styles 的責任拆分清楚

### 15.3 相容策略

- 不影響既有 router 結構
- 不影響 Hash History 導航方式
- 不影響 API request 路徑
- 不影響 auth 流程
- 不改變既有欄位命名與送出 payload 結構

## 16. 驗證策略

完成後至少需覆蓋以下驗證：

- 主要頁面手動視覺檢查
- 桌面與手機寬度的版面檢查
- 登入、登出、個人資料更新、文章建立 / 編輯 / 刪除流程不回歸
- loading / error / empty state 顯示正常
- build 與既有測試可維持通過

## 17. 已知風險

### 17.1 視覺過重風險

深色 neomorphic 若陰影過多，容易造成：

- 對比不足
- 元件邊界不清
- 後台掃描效率下降

對策：後台採同語言但較克制版本，弱化裝飾、強化資訊結構。

### 17.2 資料量不足風險

部分範例頁面依賴較豐富的展示資料。現有資料較少時，可能造成畫面空洞。

對策：增加描述性文案、操作導引、分區容器與狀態包裝，不補假資料。

### 17.3 可讀性風險

文章詳情頁若過度追求風格，可能犧牲長文閱讀體驗。

對策：文章頁裝飾集中在外層容器，正文區以排版優先。

### 17.4 開發複雜度風險

若未先建立 token，逐頁直改容易造成樣式分裂。

對策：先完成 theme 基礎，再做 layout，最後處理各頁。

## 18. 驗收標準

完成後應滿足以下條件：

- 全站視覺語言明顯貼近 `page_example`
- 前台、登入流程、後台具一致設計語言
- 現有主要功能皆可照常使用
- 無需後端新增 API 即可成立
- 所有主要頁面在桌面與手機尺寸均可正常使用
- 表單、按鈕、列表、訊息狀態皆有一致樣式
- 深色主題下仍維持可接受的可讀性與操作辨識
- 缺圖、缺作者、缺日期、空列表等 fallback 均有一致處理
- 驗證策略列出的檢查項目皆可完成

## 19. 待確認事項

經本次自查後，尚無阻止實作的未決需求。以下項目可由實作階段自行判斷，不需另開需求阻塞：

- Public Layout 與 Admin Layout 採頂部導覽或局部側欄的最終形式
- 是否額外加入不依賴後端的新靜態裝飾區塊
- 封面圖 fallback 採抽象幾何、品牌字首或純漸層版本

若後續實作中發現資料不足以支撐特定畫面，再回到 spec 補充，而不是先假設新的 API 欄位。

## 20. 推薦實作順序

1. 建立全域 theme token 與基礎元素樣式
2. 重構 `PublicLayout` 與 `AdminLayout`
3. 完成 auth 類頁面
4. 完成首頁與文章詳情頁
5. 完成後台列表、dashboard、編輯頁
6. 補強 loading / error / empty states
7. 進行響應式與可讀性調整

## 21. 結論

本次 UI 改版可行，且適合以「高度貼近視覺語言，但不硬搬靜態版型」的方式進行。最重要的成功條件不是複製範例畫面，而是先建立一套可重用的深色 neomorphic 設計基底，再將其穩定套用到現有前台與後台頁面。
